# SolarSimz 자동 연구 및 재귀 개선 결과

2026-09-06, 파일럿 운영 저장소를 대상으로 Inner 실험 6회와 Outer 전략 검토 2회를 수행했다.
5개 변경을 채택했고, 반복 알람 확인 비용이 늘어난 1개 변경은 실제 Git revert로 되돌렸다.
실제 앱 변경은 `src/features/pilot/ops-repository.ts` 한 파일이다.

## 측정 결과

고정 점수는 시나리오별 `SQL 실행 횟수 × 10 + JavaScript로 반환한 행 수`의 합이다.
API 지연 시간, SQLite 내부 스캔량, 실제 운영 서버의 속도 개선률을 뜻하지 않는다.

| 평가 | 기준선 | 최종 | 작업량 감소 |
|---|---:|---:|---:|
| Inner: 검수 32개·계측 2,400개·추가 관제점 16개 | 2,971 | 317 | 89.33% |
| Outer: 검수 137개·계측 8,760개·추가 관제점 64개 | 10,707 | 797 | 92.56% |

| 동작 | 변경 전 | 변경 후 |
|---|---:|---:|
| 검수 20건 조회 SQL | 21회 | 2회 |
| 검수 100건 조회 SQL | 101회 | 2회 |
| 운영 요약에서 읽는 계측 | 2,400 / 8,760행 | 1행 |
| 매핑 검사에서 읽는 관제점 | 18 / 66행 | 1행 |
| 일일 확인 생성·갱신 SQL | 4회 | 3회 |
| 최초 알람 확인 SQL | 3회 | 2회 |
| 반복 알람 확인 SQL | 1회 | 1회 |

큰 효과 순으로 최근 계측 한 행 조회, 검수 항목 일괄 조회, 지정 관제점 조회가 상위 3개다.

## 재귀 개선에서 바뀐 전략

1세대는 N+1 조회·전체 계측 로딩·일일 확인의 중복 조회를 제거했다. 이후 Outer 점수와 남은 비용을 읽어 매핑 및 알람으로 우선순위를 옮겼다.
2세대는 일일 확인에서 성공했던 선행 조회 제거를 알람에 적용해 보았다. 전체 점수는 좋아졌지만 반복 ack가 1→2 SQL로 회귀해 폐기했다.
그 관찰을 연구 지침에 반영하여 마지막 실험에서는 조기 반환을 보존하고 성공 후 재조회만 제거했다.

평가와 메타 평가 및 기존 소스·테스트 등 134개 파일의 SHA-256을 기준선 전에 동결했다. 실험 중 변경한 것은 대상 구현, 전략, 결과 기록이다.
`metric_weights.json`은 다음 실험의 우선순위에만 사용하며 고정 점수의 가중치는 바꾸지 않는다.
이는 프로젝트 코드와 연구 전략의 반복 개선이다. 모델 자체의 가중치를 학습시키거나 상주 서비스를 실행한 것은 아니다.

## 검증

- 기존 단위·저장소·API 테스트 67개 통과.
- 추가 고정 워크로드 2개 통과: 응답 전체 비교, 목록 제한, 항목 없는 검수, 테넌트/게이트웨이 격리, 다른 데이터 소스, 갱신 직후 최신성, 매핑 대소문자, 서울 날짜 경계, 일일 확인 ID 유지, 중복 ack의 최초 확인자·시각 유지.
- 타입 검사 통과.
- lint 오류 0개, 기존 경고 38개.
- Next.js 프로덕션 빌드 통과.
- Chrome 브라우저 E2E 12개 통과(32.9초): CRUD, 권한, 모바일, 필터, 입력 오류, 최신 상세, 오류 상태, 세션 만료, 수정 충돌, 키보드 포커스.

E2E 개발 서버가 tsconfig.json에 임시 빌드 타입 경로를 자동 추가했다. 이를 기준선의 원래 설정으로 복원한 뒤 동결 파일 해시와 타입 검사를 다시 확인했다.

SQLite 메모리 DB의 작은/큰 고정 데이터에서 평가했다. 시간은 참고치로만 수집했으며 통계적 응답 시간 개선을 주장하지 않는다.
직접적인 동시 연결 ack 경쟁은 이번 고정 평가에 포함되지 않았다. 코드에는 다른 연결이 먼저 확인했을 때 결과를 다시 읽는 경로를 유지했다.

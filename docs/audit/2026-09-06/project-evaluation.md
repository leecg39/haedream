## 4. 큰 감점 요인과 재현 근거

### ① 기업·한전 업무 API에 인증 경계가 없습니다 — 최우선

쿠키 없는 요청에서 시설 API는 401을 반환하지만, 기업·한전 API는 데이터를 반환합니다. 별도 평가용 DB와 빈 한전 자격증명 파일을 사용하는 로컬 프로덕션 서버에서 확인했습니다.

| 로그인하지 않은 요청 | 결과 |
|---|---|
| `GET /api/auth/session` | 401 |
| `GET /api/facilities` | 401 |
| `GET /api/firm` | 200, 업체 1,654건 반환 |
| `GET /api/firm/121` | 200, 동일한 전체 업체 목록 반환 |
| `GET /api/kepco/status` | 200, 1,431건 반환 |
| `GET /api/kepco/firm/7` | 200; 빈 평가 DB의 상세 구조 반환 |
| `POST /api/firm` + 동일 출처 헤더 | 201, 평가용 업체 생성 |
| `POST /api/kepco/collect` + 동일 출처 헤더 | 200, 자격증명 없는 업체의 `no_credentials` 결과 및 로그 생성 |

실제 한전 계정으로 수집을 실행하지 않았습니다. 마지막 검증은 인증되지 않은 요청이 수집 처리까지 도달함을 확인한 것입니다. 동일 출처 검사는 CSRF 방어이며 사용자 인증을 대신하지 않습니다. 모든 요청에서 권한을 검증하라는 [OWASP의 원칙](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html#validate-the-permissions-on-every-request)에 비추어, 이 경로들에도 사용자·업체 범위 검사가 필요합니다.

FIT 로그인은 비어 있지 않은 임의의 아이디·비밀번호를 넣으면 서버 검증 없이 `/fit/peak`로 이동하며 세션 쿠키도 만들지 않습니다. 데모 로그인 동작과 실제 시설 로그인 동작이 서로 다릅니다. [FIT 로그인](/Users/user01/Desktop/SolarSimz/src/components/fit/FitLoginForm.tsx:60), [기업 API](/Users/user01/Desktop/SolarSimz/src/app/api/firm/route.ts:26), [한전 API](/Users/user01/Desktop/SolarSimz/src/app/api/[...path]/route.ts:155)

근거: [API 검증](evidence/api-probes.json), [브라우저·조회 검증](evidence/runtime-summary.json). 최초 `127.0.0.1` 출처의 쓰기 요청은 403이었고, 앱의 `localhost` 출처로 재검증하면 위 결과가 나왔습니다. 이 초기 403을 인증 방어로 오인하지 않도록 두 기록을 함께 보존했습니다.

### ② 고객정보가 공개 JavaScript 번들에도 포함됩니다 — 최우선

1,114,819바이트 크기의 생성된 클라이언트 청크에서 fixture와 일치하는 연락처·주소·한전고객번호 문자열이 확인됐습니다. 고유값 기준으로 전화번호 67개, 주소 1,467개, 고객번호 1,418개가 일치했습니다. 이 집계는 길이 8자 이상 문자열의 일치를 센 것이며 사람 수를 뜻하지 않습니다.

해당 `/_next/static/chunks/...js` 주소는 **쿠키 없이 HTTP 200**으로 내려옵니다. API에 인증을 추가해도 이미 공개된 번들에 포함된 데이터는 보호되지 않습니다. 공유 상수와 실제 업체 JSON을 분리하고 서버에서 인증 후 필요한 필드만 전달해야 합니다.

fixture 자체에도 주소 1,636행, 담당자 227행, 전화번호 91행, 대표자 469행이 채워져 있습니다. 실제 업무 덤프라는 설명과 함께 Git 추적 대상입니다. 공개 가능한 합성 fixture로 교체하고 데이터 공유 범위와 이력을 점검해야 합니다. 한전 비밀번호는 이 fixture에 없으며 별도 로컬 파일로 분리되어 있다는 점은 긍정적입니다.

### ⑤ 수집 API가 잘못된 입력을 전체 수집 요청으로 해석할 수 있습니다

`readJson(req).catch(() => ({}))`는 잘못된 JSON, 잘못된 Content-Type, 크기 제한 오류를 빈 객체로 바꿉니다. 이후 `fid`가 없으면 비밀번호 보유 업체 전체를 대상으로 삼습니다. 빈 자격증명 파일을 둔 검증에서는 잘못된 JSON에 정상적인 400 대신 대상 없음 404가 나왔습니다. 자격증명이 있는 환경의 전체 수집은 코드에서 확인한 조건부 위험이며 실행하지 않았습니다.

입력을 strict 스키마로 검증하고 ‘선택 업체 수집’과 ‘전체 수집’을 명시적으로 구분해야 합니다. 현재의 배치 잠금 조회는 수동 요청 자체가 잠금을 획득하는 구조가 아니며, 외부 fetch에도 명시적 요청 시간 제한이 보이지 않습니다. 장시간 작업의 중복 실행·타임아웃·재시작 기준을 보강할 필요가 있습니다. [입력 처리](/Users/user01/Desktop/SolarSimz/src/app/api/[...path]/route.ts:248), [순차 수집](/Users/user01/Desktop/SolarSimz/src/lib/kepco/collect.ts:307)

### ⑥ 모바일과 접근성 품질이 화면마다 다릅니다

390×844 화면에서 `/fit/firm`의 콘텐츠가 오른쪽 좁은 영역에 몰리고 표의 대부분이 잘립니다. 테이블 너비는 약 1,257px, 문서 너비는 400px로 측정됐습니다. 전체 문서의 넘침이 10px라는 수치보다 실제 사용 가능한 표 영역이 매우 좁다는 시각적 문제가 더 큽니다. [모바일 화면](evidence/fit-firm-mobile.png)

시설 관리에는 포커스 제어와 필드 오류 연결이 있지만 FIT 기업관리의 ‘추가·엑셀·프린트’는 `span role="button"`에 클릭만 연결되어 있습니다. 해당 요소에는 `tabIndex`와 키보드 처리도 없습니다. FIT 로그인 입력에는 명시적인 label/aria-label 연결이 없습니다. 전체 WCAG 적합성 검사를 실행한 것은 아니며, 코드와 제한된 DOM 점검에서 확인한 항목입니다.

### ⑦ 운영 자동화와 유지보수에 추가 작업이 필요합니다

프로젝트 안에서 CI 워크플로, 배포 설정, 자동 백업 작업, 실제 주기적 수집 등록, 가동률 알림의 실행 증거는 찾지 못했습니다. 저장소 밖에 별도로 구성되어 있을 가능성은 평가하지 않았습니다. 백업·복구와 SQLite 단일 인스턴스 제약은 문서화되어 있습니다. [운영 문서](/Users/user01/Desktop/SolarSimz/docs/facility-crud-design.md:177)

`FacilitiesManager.tsx`는 1,836줄, `AdminTablePage.tsx`는 974줄입니다. 업무 로직과 폼·모달·표·접근성 처리가 한 파일에 모여 있습니다. 파일을 작게 만드는 것 자체보다, 시설 폼·목록 조회·편집 충돌 처리를 독립적으로 변경할 수 있게 분리하는 것이 중요합니다.

`GET /api/firm`은 약 1.07MB의 JSON을 반환합니다. 선택 목록에 필요한 ID·이름과 상세 업무 필드를 나누고 목록 검색·페이지 이동을 서버에서 수행하면 불필요한 데이터 전송과 클라이언트 정렬 부담을 줄일 수 있습니다. 이 수치는 압축 전 응답 본문 크기이며 실제 네트워크 전송량과 같지 않습니다.

## 6. 보안·라이선스·개인정보 평가

별도의 [감사 보고서](../audit-report-2026-09-06.md)에 심각도와 조치를 정리했습니다. 외부 공개 운영 기준의 주요 발견은 인증 누락, 고객정보 번들 노출, 수집 입력의 잘못된 기본 동작입니다. 배포 서버가 실제 인터넷에 공개되어 있는지는 확인하지 않았습니다.

좋은 보안 조치도 있습니다. 시설 권한·테넌트 검사, bcrypt 비밀번호 해시, DB에 원문 대신 해시를 저장하는 세션, HttpOnly 쿠키, strict Zod 검증, SQL 파라미터 바인딩, 감사 로그 보호, 데모 시드의 명시적 허용 설정이 구현되어 있습니다. 이 기반을 새 업무 API에 일관되게 적용하는 것이 효율적입니다.

라이선스는 lockfile 509개 패키지 항목의 메타데이터를 집계했습니다. 원본 사이트에서 복제한 디자인·이미지·폰트·JS의 재배포 권리 확인 자료는 별도로 필요합니다. `agentation`은 PolyForm Shield로 표시되어 있고 현재 React 화면에서는 개발 모드에만 렌더링됩니다. 실제 제품에 포함해 배포할 경우의 조건은 [프로젝트 라이선스](https://github.com/benjitaylor/agentation/blob/main/LICENSE)와 [공식 배포 안내](https://www.agentation.com/)에 따라 확인해야 합니다. 확인되지 않은 충돌을 위반으로 단정하지 않았습니다.
